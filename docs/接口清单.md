> 统一前缀 `/api`；统一响应体 `{ code, msg, data, traceId }`；分页统一 `{ pageNum, pageSize, total, list }`。

## 3. 客户　⏸ 本期不做

需求确认：**客户名称在订单上手填**，不建客户档案。

理由很实际：如果先建客户档案才能下单，客服会为了"少点几下"绕开系统用微信报单，
最后系统里一条数据都没有。`client` / `client_contact` 两张表保留未删，
等真正需要"按客户看复购、看欠款账龄"时再启用，届时用「历史订单批量归属客户」补数据。

## 4. 价目　⏸ 本期不做

需求确认：**单价由主管在录单时手填**。

同一个"画册设计"，16 页和 48 页不是一个价，强行上价目表会变成"建了一堆品项，每单还是手改"。
`order_item.unit_price` 本来就是快照列，手填后立刻固化 ——
明年调价、后年改规则，这一行的金额都不会变，历史业绩不会漂移。

## 8.1 工资核算　✅ 已实现

工资 = 底薪 + 业绩 × 阶梯比例。业绩口径与业绩页完全一致（已到账回款），不另算一套。

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/salary/my?period=yyyy-MM` | 我的工资单：业绩、命中比例、提成、应发、距下一档差多少 | 全（仅本人） |
| GET | `/salary/team?period=&keyword=` | 团队工资表，按应发降序 | 主管/管理员 |
| GET | `/salary/tiers` | 提成阶梯列表（员工可见，用于自己核对） | 全 |
| PUT | `/salary/tiers` | 整表替换阶梯（断档、重叠、首档不从 0 开始都会被拒） | 仅管理员 |
| GET | `/salary/base-policy` | 分级底薪：普通 1500 / 精英 2000 / 主管 3000（员工可见，用于核对） | 全 |
| PUT | `/salary/base-policy` | 整表替换底薪政策；缺级别 → 44006，负数 → 40000 | 仅管理员 |
| PUT | `/salary/base/{employeeId}` | 单独指定某人底薪（记日志：谁把谁从多少改成多少）；body 传 `{}` 即撤销特例、恢复按级别 | 主管/管理员 |

**底薪为什么分两层**
级别政策（`salary_base_policy`）是默认值，个人指定（`employee.base_salary`）是特例。
只有需要给个别人谈特殊待遇时才写第二层；撤销时把它清回 NULL，就自动跟随级别政策 ——
若改成"填回政策数字"，下次调政策这个人就跟不上了。

**工资单返回的底薪字段**
`baseSalary` 金额、`empLevel` / `empLevelLabel` 级别、`baseSalarySource`（`LEVEL` 按级别 / `PERSONAL` 个人指定）、
`baseSalaryNote`（如「精英员工 · 按级别 2000.00」）。员工看到数字的同时就知道它是怎么来的。

**为什么 `/salary/my` 不接收 employeeId**
不接收参数就不存在"改参数越权"这条攻击面。要看别人走 `/salary/team`，那条路径有独立的范围校验。
工资比业绩敏感得多：业绩是"你做了多少"，工资是"公司给你多少钱"，一旦全员可见就是人事事故。

## 关键接口的实现约束

**`POST /payments/{id}/allocate`** —— 全系统唯一会生成业绩的入口：
1. 校验核销总额 ≤ 回款金额；订单已核销额 ≤ 订单总额（乐观锁）
2. 调 `PerformanceAllocator.allocate(核销额, 明细行)` 得到分摊结果
3. 逐条插入 `performance_ledger`，`idem_key` 唯一索引兜底防重
4. 更新 `receivable_plan.received_amount`、订单收款状态
5. 刷新 `monthly_perf_summary`
6. 以上全部在同一事务内，任一步失败整体回滚

**`GET /performance/my/items`** —— 行级隔离的唯一防线：
不允许"查全量再在内存里过滤"。SQL 直接带 `AND a.employee_id = #{currentEmpId}`，
且返回 VO 不含 `order.total_amount`，从接口层面就看不到整单金额。

**`POST /orders/{id}/price`** —— 签单额生成点：
明细保存后重算 `total_amount` 与 `perf_base_amount`，校验每行比例合计 = 100%，
再为每个分成人生成一条 `ledger_type=1 (SIGN)` 流水，`period` = 签单月。

## 11. 收款计划与催收　✅ v2.1 已实现

> 口径：定价确认时自动生成收款计划 —— 订金 30%（`studio.receivable.deposit-percent`，可配）
> 应收日=签单日；尾款 70%（差额法）应收日=交付月月末（未交付取签单月月末）。
> **月末催收窗口** = 每月最后 N 天（`studio.receivable.window-days`，默认 3，月末反推，2 月/闰年自动正确）。

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/receivables/summary` | 概览：窗口区间/是否在窗口内/距窗口天数、待收合计、窗口内待催、逾期、本月已回款、承诺数、本月催收次数 | 主/客/财/老 |
| GET | `/receivables/collection` | 催收清单，`scope=ALL\|WINDOW\|OVERDUE` + `keyword`；每行含逾期天数、是否窗口内、承诺是否跳票、客服电话 | 主/客/财/老 |
| GET | `/receivables/orders/{orderId}/plans` | 某订单的收款计划（订单详情抽屉用） | 主/客/财/老 |
| POST | `/receivables/{planId}/collect` | 登记一次催收：方式 + 结果 + 客户承诺（日期/金额）+ 备注；计划行催收次数 +1 并刷新承诺 | 主/客/财/老 |
| GET | `/receivables/orders/{orderId}/logs` | 某订单的催收历史（倒序） | 主/客/财/老 |
| POST | `/receivables/rebuild` | 为历史订单幂等补建计划并重算已收 | 老 |

实现约束：
- 计划金额不允许手工改 —— 由订单总额推导；改金额走重新定价。
- 已收金额由回款核销**重算**（按期次 FIFO：订金先收满再冲尾款），不接收人工输入。
- 回款登记（`POST /orders/{id}/payments`）事务内同步 `recalc`；交付（status→4）事务内把尾款应收日挪到交付月月末。
- 迁移 V8 已为存量已定价订单回填计划与已收金额。

## 13. 报表导出（xlsx）　✅ v2.1 已实现

> 全部返回文件流：`Content-Disposition` 带中文文件名（`filename*` RFC 5987），
> `Cache-Control: no-store`；金额单元格保持数值 + `#,##0.00` 格式（可直接求和排序）。
> **每次导出写一条 `REPORT` 审计**（谁、导了什么、多少行）—— 导出即数据出系统，必须留痕。

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/reports/salary` | 团队工资表，`period/keyword`；含级别、底薪来源、计算口径 | 主/老 |
| GET | `/reports/orders` | 订单台账（与列表页相同筛选，上限 5000 行），含未收列 | 主/财/老 |
| GET | `/reports/receivables` | 催收清单，`scope/keyword`，含客服电话与承诺；超过 5000 行报错引导缩小范围 | 主/客/财/老 |
| GET | `/reports/invoices` | 开票台账，`status/period/keyword`，含税额/不含税三列；超过 5000 行报错引导缩小范围 | 主/财/老 |
| GET | `/reports/performance` | 我的业绩明细 —— 人人可导，但服务端强制只含自己参与的单 | 全 |

> 前端下载走独立 axios 实例（blob，且失败时解析 blob 里的 JSON 给出后端中文提示），
> 不复用解包 `R<T>` 的实例。

## 14. 安全与性能加固　✅ v2.2

| 项 | 说明 |
|---|---|
| 登录锁定 | 窗口内失败 5 次后**固定锁定 15 分钟**（`40103`）；锁定期间直接拒绝不校验密码；失败记录表超 10000 个用户名时拒绝而非放行。窗口 `LoginAttemptGuard.WINDOW` 可测调整 |
| 密码清理 | 源码注释中的真实密码示例已删除（经登录验证该密码已失效，无需轮换） |
| 上传上限 | `max-file-size` 200MB → **50MB**（无配额前提下收紧磁盘耗尽风险） |
| 上传事务 | 文件落盘移出事务（编程式事务只包 insert），大文件上传不再占用数据库连接 |
| 开票索引 | V10 新增 `invoice.idx_applied_at(applied_at)`，按月筛选台账不再全表扫 |
| 台账分页 | `GET /invoices` 分页 + 每行子查询改派生表 JOIN（1000 张票从 2000 次聚合降到 2 次） |
| 导出上限 | 催收/开票导出加 5000 行上限，超额报错引导缩小范围（订单导出原有） |
